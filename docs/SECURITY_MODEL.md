# 安全模型

> 描述**终局**安全模型（⑤⑥ 全部完成后）。标 ✅ 的已实现并验证，⏳ 的在路线图上。
> 最后更新：2026-09-05。
>
> 安全不是形容词。本文按「防谁 → 靠什么 → 怎么验证」组织，每条保证都要能被证伪。

---

## 一、第一性原理

整个模型只有一条判据：

> **假设对方拿到了他能拿到的一切，攻击是否仍然不可行。**

能被"只要谁不把 X 给错人就没事"这类话术描述的保证，都不算保证。按这条判据，安全模型
做的是三个转换：

| 从 | 到 | 体现在 |
|---|---|---|
| 约定 | 密码学 | 冒充防护不再依赖"别把密钥给错人" |
| 默认允许 | 默认拒绝 | 三处 fail-closed |
| 单点信任 | 分层收敛 | 任一凭据泄露的爆炸半径都被限定 |

---

## 二、威胁模型：防谁，不防谁

| 攻击者 | 他拥有什么 | 结论 |
|---|---|---|
| 外部无凭据者 | 网络可达性 | ✅ 防住 |
| **持有某服务密钥者**（外包 / 被攻破的服务） | 一把派生密钥 + 全部公开信息 | ✅ 只能是他自己 |
| **拿到数据库的人** | 服务目录全表 | ✅ 无身份影响 |
| 越权的内部用户 | 一个低权限管理账号 | ✅ 防住 |
| **不可信的代码提供方** | 交付的代码在你的环境里运行 | ⚠️ 靠隔离层，不靠代码 |
| 平台自己 | 主密钥 | ❌ **不防**，见 §六 |

**没写在表里的攻击者不在防护范围内。** 比如拿到主密钥的人、能改部署配置的人、
能改数据库的人——他们不是本模型的对手。

---

## 三、三层防御

每层独立成立，**一层的保证不依赖另一层没被攻破**。

| 层 | 回答 | 失效后果 | 保证来自 | 状态 |
|---|---|---|---|---|
| 身份层 | 你是谁 | 冒充 | 密码学 | ✅ |
| 授权层 | 你能做什么 | 越权 | 数据（目录 `grants`） | ✅ |
| 隔离层 | 你够得着什么 | 绕过前两层 | 部署（独立库/进程/域名） | ⏳ ⑤ |

缺任一层，另外两层都会被绕过。例：外包服务身份对、grants 也校验了，但他直接连数据库
读全表——前两层白做。这正是当前 `partner-service` 用 root 连共用库的状态。

---

## 四、攻击树：具体路径与拦截点

这是"为什么安全"的可检验形式。每条路径标注**在哪一层被挡、靠什么、是否已实测**。

### A. 我想冒充另一个服务

| # | 攻击路径 | 拦截点 | 实测 |
|---|---|---|---|
| A1 | 伪造 token，随便签 | 身份层：无有效签名 | ✅ |
| A2 | **持有 partner-service 密钥，签 `sub=optimus-api`** | 身份层：验签用 `sub` 所指服务的密钥，与签名者手里的对不上 | ✅ 实测 `active:false` |
| A3 | 用主密钥直接签（旧共享模型） | 身份层：主密钥不是任何服务的签名密钥 | ✅ 实测 `active:false` |
| A4 | 从自己的派生密钥反推主密钥 | 身份层：HKDF 单向 | 密码学性质 |
| A5 | 从自己的派生密钥导出别人的 | 身份层：需要主密钥才能派生 | 密码学性质 |
| A6 | 脱库拿服务目录，找密钥 | 身份层：**表里没有任何可签发的秘密**（派生密钥不落地，验签时现算） | ✅ 已核对表结构 |
| A7 | 复用一个已下线服务的旧 token | 身份层：自省反查 `enabled`，下线即失效 | ✅ 有单测 |

> A2 是整个身份层的核心：攻击者**控制得了声明（`sub`），控制不了声明对应的密钥**。

### B. 我身份是真的，但想干超出授权的事

| # | 攻击路径 | 拦截点 | 实测 |
|---|---|---|---|
| B1 | 三方服务登记完就调受保护接口 | 授权层：三方默认 `grants=[]` | ✅ 实测落库为 `[]` |
| B2 | **转发一个超管 token 去提权** | 授权层：`@RequireGrant` 只认 service token，用户 token 过不了验签 | ✅ 有单测 |
| B3 | 权限被收回后，用旧 token 打时间差 | 授权层：**grants 不写进 token，每次现读**，撤销无盲区 | ✅ 实测同一 token 未重签即反映新授权 |
| B4 | 配一个拼错的 grant 蒙混 | 授权层：白名单校验 | ✅ 实测 400「未知的 grant」 |
| B5 | 改个服务名把授权重置回默认集 | 授权层：更新不传 grants 则保持原样 | ✅ 实测授权不变 |
| B6 | 绕过网关直连服务源 | 授权层：**校验在被调用方**，不在网关 | 有单测 |
| B7 | 调一个没声明权限语义的管理接口 | 授权层：fail-closed，未声明一律 403 | 已有（08-24） |

> B6 不是理论问题：embed 管理页本来就是浏览器直连子服务源的。授权放网关会让这条
> 路径出现真空。

### C. 我绕过应用层，直接动数据

| # | 攻击路径 | 拦截点 | 状态 |
|---|---|---|---|
| C1 | 三方服务直连平台库读全表 | 隔离层：三方独立数据库实例 | ⏳ 进了检查清单，**代码管不到** |
| C2 | 业务服务 JOIN 别人的表 | 隔离层：DB 账号只授自己的表 | ⏳ 技术债，当前是 root |
| C3 | 通过网关把流量导到不该去的服务 | 隔离层：路由权威来自服务目录 | ⏳ ⑤ 未做 |

**C 类是当前最弱的一环。** C1/C2 现在只有流程约束，没有机制约束。

## 五、三处 fail-closed

默认拒绝出现在三个地方，语义一致：

1. **管理接口** —— 没挂 `@Perm` / `@AllowNoPerm` / `@RequireSuperAdmin` 的一律 403
2. **服务能力** —— 未被授予对应 grant 一律 403
3. **三方登记** —— 登记完 `grants` 为空，什么都调不了

> **"登记过"不等于"可信"。** 这是外包场景的核心，也是与"任何持有 service token
> 的服务都能调"这种设计的根本区别。

## 六、爆炸半径

| 泄露物 | 后果 |
|---|---|
| 某服务的派生密钥 | 只能冒充该服务本身 |
| 服务目录全表 | 无身份影响 |
| 某服务的数据库账号 | 只够得着自己的表（⏳ 隔离层建成后） |
| **主密钥** | **全平台沦陷** ← 唯一单点 |

主密钥是有意保留的单点：消除它需要非对称方案（各服务持私钥、平台只存公钥），
代价是引入密钥分发与轮换管理。`platform-trust-model/design.md` 已留好升级路径，
触发条件是**第一个真实三方服务上线**。

---

## 七、明确不保证的四件事

1. **防不住平台自己。** 持有主密钥即可签发任意身份。防的是服务互相冒充与外部持密钥者。
2. **没有主密钥轮换。** 有意省略（当前在线服务仅 1 个），轮换会让所有派生密钥同时失效。
   **这是已记录的欠账，服务变多后必须补。**
3. **隔离层靠部署，代码管不到。** 没有代码能阻止部署时把三方服务配成共用库。
4. **没有服务间调用的审计与限流。** `design.md` 的 Non-Goals 明确排除。

## 八、三方场景：已定方向，暂缓实施

**2026-09-05 范围决策：当前只做一方与二方，三方（外部合作方）场景后续再启动。**

理由：三方是当前不存在的场景，而一方二方是每天在跑的。为不存在的场景先建能力，
容易设计出用不上的东西。

**已定的方向（启动时直接按此实施，不必重新推导）：不接受成品交付，只接受源代码，
由平台审计、构建、部署。** 四个关键要素：

| 要素 | 作用 |
|---|---|
| 源码交付 + 静态审计 | 可扫出网调用、数据落盘、可疑依赖 |
| 构建期密钥注入 | 合作方全程接触不到任何凭据 |
| 默认禁止出网 + 白名单 | 关闭数据外传的主通道 |
| 存储由平台提供 | 对方没有自己的库可写 |

这四条叠加后，"私自留存并带走"的路径基本封闭。但**仍不宣称"绝对安全"**，三条边界：

1. **审计不能穷尽** —— 动态加载、依赖包内的代码、条件触发逻辑，静态扫描可能漏
2. **授权内的数据本就可用** —— 功能要读数据才能工作，读到后在进程内如何使用，审计管不到
3. **合法通道可夹带** —— 例如渲染给终端用户的内容里携带信息

准确表述是**可控、可审计、可追溯**。对专业采购方而言，这个表述比"绝对安全"更可信。

**同时暂缓的三方专属能力**：用户标识化名（pairwise ID）、合作方数据托管、
用户 token 转发缺口的治理（一方场景下同一批人同一部署，风险可接受）。

> ⚠️ 与此相对，**积分发放那组约束不属于三方专属，一方场景同样需要**：
> 幂等键当前由事件内容生成（调用方能构造事件就能绕过）、发放无额度上限、
> 发放无审计。这些是纯粹的业务健壮性问题，与信任级别无关，不随本节一起暂缓。

## 九、怎么复验

任何人都可以用这几步证伪身份层与授权层（需 Docker + MySQL + optimus-api）：

```bash
# 冒充：用 A 的派生密钥签 sub=B，期望 active:false
# 旧模型：用主密钥直接签，期望 active:false
# 撤销无盲区：改 grants 后用同一个未重签的 token 自省，期望立即反映
curl -s -X POST localhost:8084/api/auth/introspect \
  -H 'Content-Type: application/json' \
  -d '{"token":"<TOKEN>","type":"service"}'
```

派生算法（两个包各一份实现，由共享测试向量锚定）：

```
HKDF-SHA256(ikm=主密钥, salt="optimus-service-token-v1", info=serviceKey, len=32) → hex
```

测试基线：optimus-api 155/155、server-sdk 13/13、partner-service 110/110。
