01这份文档解决什么

Optimus CMS 正从单体演进为单机规模的微服务：业务域按团队归属拆成独立服务， 并且一方、二方、三方团队都会开发子应用（外包与低代码是既定场景）。

在这个前提下，原有的权限模型有三处不够用：

  • 权限码是不透明的扁平字符串，平台无法判断一个码属于谁、能做什么、有没有越界
  • 判定逻辑在四个地方各存一份（平台守卫、子服务守卫、管理端菜单过滤、子应用前端）
  • 没有操作粒度 —— 无法表达"能看订单但不能改"
文档状态

本文档定义目标模型。文中凡标注 已实现 的是当前代码的真实状态， 目标 的尚未开始， 缺陷 的是已验证存在的问题。不要把目标当现状读。

02现状（写在设计之前）

设计必须建立在事实上，所以先把当前代码的真实状态钉住。

唯一生效的机制：权限码

op_sys_user_role (user → role)
    JOIN op_sys_role_menu (role → permission_code)
    → 去重 → user.perms: string[]

超管特判：op_sys_user.type = 0 → perms = ["*"]，不比对直接放行。

消费方判据状态
接口@Perm("X") → perms.includes("X")，精确匹配已实现
菜单menu.code → perms.includes(code)已实现
服务能力@RequireGrant("user-profile:read-full") → 服务目录的 grants已实现
值得保留的性质

同一个码同时管接口和菜单。这避免了"菜单看得见、接口 403"这类不一致， 目标模型保留这条。

接口 fail-closed。没挂 @Perm / @AllowNoPerm / @RequireSuperAdmin 一律 403 —— 2026-08-24 审计时改的，此前默认放行， 当时发现"改积分余额、清空数据、读全量订单"等接口都在裸奔。

空转与缺失

项真实状态
CASL后端 @CheckPolicies 与 PoliciesGuard 零调用点；前端 ability 建了、update() 了，ability.can / <Can> 零消费；generateCASLRules 把所有码降级成 {action:'read'}
按钮级权限已被移除（routes.js: // BUTTON: 3 - 已移除），无操作粒度
数据权限无 dataScope / deptId / 行级概念；leaderRoleIds 查了没人用
权限码字典不存在 —— 码是自由字符串，隐式由代码定义
菜单存储不在数据库里 —— SYSTEM_ROUTES 是前端常量（40 节点）
RolesGuard权限比对整段被注释、无条件 return true；仍有 2 个调用点
op_sys_document_perm文档模块自己的资源级权限表，与主体系平行 —— 全系统唯一的"某人对某条记录有权限"

已验证的四个缺陷

缺陷后果验证方式
菜单顶层泄漏 缺陷filterMenus 里 children.some(c => c.isDynamicMenu) 恒为真，父节点无条件通过过滤；末尾 menu.path || children.length 又因有 path 留下它 —— 无任何权限的人也能看见应用入口实测确认

config_center 替换而非合并 缺陷children: dynamicDocMenus 直接覆盖，谁给它加静态子菜单会被静默冲掉读代码确认
泄漏程度要说准

顶层泄漏是菜单显示层面的，不是越权。pages/embed/index.jsx 进页前会再校验一次，真正的门在子应用后端。后果是"看得见入口、点进去 403"， 外加能从侧边栏看出平台上装了哪些应用。

03硬约束：从终局架构反推

不从"改动最小"出发，从架构必须承接的场景反推。

约束来自推论
多方开发
一/二/三方团队开发子应用，声明自己的权限需求，但不能自己授权		 外包 + 低代码是既定场景 权限码必须可归属、可校验
同一份判定在多处跑
平台守卫、子服务守卫、管理端菜单、子应用 iframe 内		 L2 服务独立进程，不共享代码就会各写各的 判定核心必须零依赖、可跨进程
主体隔离不能破
服务的能力不能靠转发高权限用户 token 获得		 信任模型（已拍板） 统一形态，不统一授权来源
L1 不认识任何 L2 分层架构的根基 平台不能理解业务域的数据模型

第四条是后面许多结论的源头，尤其是第 8 节的分界线。

04核心：三段式权限码

扁平码 OrderManagement 的根本问题不是不好看，是对平台不透明 —— 平台无法回答"这个码属于谁、能干什么、越界没有"。

partner:campaign:write
namespace归属。一个服务只能声明自己命名空间下的码
resource对什么。同一服务的不同资源可区分
action做什么。当前完全缺失的维度

通配

模式匹配用途
partner:campaign:*该资源的全部动作业务管理员
partner:* / partner:*:*该命名空间全部服务负责人
*全部，等价 *:*:*超管

现在的超管 * 只是一处特判逻辑；升级后它变成通配规则的一个特例， 判定路径少一条分支。

与服务能力授权对齐

服务层的 grants 本来就是 user-profile:read-basic 这个形态。 三段式让用户权限与服务权限终于是同一套语法，共用同一个匹配函数。

05命名空间：安全支点

多方开发最大的风险是子应用声明一个宽松码蹭可见性 —— 比如声明 permCode: "Dashboard"，于是它的入口对所有持有工作台权限的人可见。

命名空间约束让这个风险在注册时就消失，不需要任何审批流程：

partner-service 注册 permission
    → 平台只接受 partner:* 开头的码
    → 它声明不出 platform:user:read
    → 也声明不出 Dashboard
设计取舍

此前考虑过"子应用声明建议码 + 平台批准"的机制。命名空间约束把这套机制整个省掉了 —— 一次注册时校验，比一套批准流程更简单也更严密。

命名空间的分配

  • platform —— 平台自有资源（用户、文章、文件、字典…）
  • 业务服务 —— 与服务目录的 key 绑定，登记服务时确定，之后不可改
  • 命名空间冲突在注册时拒绝，与 pathPrefix 全域唯一同理

06三类主体：统一形态，不统一来源

type Subject =
  | { type: 'admin';   codes: string[] }   // 来自 op_sys_role_menu
  | { type: 'client';  codes: string[] }   // C 端用户
  | { type: 'service'; codes: string[] }   // 来自服务目录的 grants

can(subject, 'partner:campaign:write')
不可越过的红线

同一个 evaluate、同一套码格式，但授权来源互不相通。 service 的 grants 不会因为它转发了一个管理员 token 而变多。

这条是信任模型的核心：否则任何服务只要能拿到管理员 token 就自动拥有全部能力， grants 配置形同虚设。

三个装饰器（@Perm / @RequireGrant / @ClientUserAuth） 在语义上可以收敛成一个 @RequirePermission，靠 subject type 分流 —— 但这属于第四期，不是地基。

07判定核心

evaluate(subject, required, options?) → Decision

interface Decision {
  allowed: boolean;
  /** 数据范围。第一版恒为 'all'，为将来留位 */
  scope?: 'own' | 'team' | 'all';
  /** 命中的是哪条码，排障用 */
  matched?: string;
}
为什么返回对象而不是 boolean

数据范围（scope）是迟早要加的一维。返回值从一开始就是对象， 后面加 scope 不用改所有调用点 —— 这是很便宜的前瞻。

规则链：留口子，不实现

evaluate(subject, required, { rules })   // 默认 [holdsCode]

第一版只实现"持有码"这一条。将来要加"且资源归属于自己"、 "且在时间窗内"，追加一条 rule 即可，不动核心。

08分界：平台判能力，子服务判范围

这是整个模型最关键的一条分界，也是拒绝把 ABAC 引擎作为地基的理由。

平台 L1
判定「能不能做这类事」
partner:profile:read —— 纯码匹配，跨进程只需传一个 string[]
↓ introspect / embed 握手下发 perms
业务 L2
判定「能看哪些行」
拼进 ORM 的 where 条件 —— 领域逻辑，只有 L2 自己懂

为什么必须分开

可预见的条件判定需求（渠道经理只看自己名下的合伙人、客服只看自己区域的订单、 文档权限）引用的字段属于 L2 的领域模型。 channelManagerId 存在于 partner-service 的库里，optimus-api 从来没见过它。

把两者统一，意味着平台要理解每个业务域的数据模型 —— 直接违反"L1 不认识任何 L2"。

跨进程的具体障碍

字符串码ABAC ability 对象
传递perms: string[]，introspect 与 EmbedContext.perms 天然带过去需 packRules 序列化 + 子服务重建
三方成本零依赖需安装 ABAC 引擎才能判权限
语言无关是否

scope 怎么设计

不要把 scope 编进码

partner:profile:read@own 这种写法会让码组合爆炸， 且 scope 的语义因业务而异 —— "自己的"在合伙人业务是 channelManagerId， 在订单业务是 regionId。

码只回答"能不能做这类事"，范围是独立的一维：平台负责存和传 scope（挂在角色上，跟着 introspect 下发），子服务负责翻译成 where 条件。 平台不需要知道 own 具体等于哪个字段。

09菜单模型

菜单节点声明 requires: string[]，任一命中即显示。 数组而非单值，因为一个页面常聚合多种资源。

{ title: '合伙人管理', requires: ['partner:campaign:read'] }
{ title: '数据总览',   requires: ['partner:campaign:read', 'partner:settlement:read'] }

五条判定规则

情形行为
requires 任一命中显示
自身不命中，但有子节点命中显示为分组容器，去掉 path（点它只展开，进不去页面）
自身与全部子节点都不命中整个节点消失
超管 *全见
requires 为空数组fail-closed —— 只有超管可见
第二条与第五条必须显式实现

第二条是现存泄漏的修复：不去掉 path，用户就能点进他没权限的应用默认页。

第五条钉死"空 = 最严"而非"空 = 不限制"。现在的等价物是 permCode || 'ServiceOps'（缺省从紧）， 新模型里"空数组"是个容易被误读成"无限制"的形态。

结构：两层封顶

▸ 合伙人服务          ← 应用本身，一个应用一个顶层
    └─ 合伙人管理      ← 子应用声明的页面
    └─ 外部任务审核

子菜单不需要 parent 字段 —— 父永远是所属服务。层级由结构保证，不靠数据表达。

节点也可配置挂载点，挂到某个已有菜单下（如把一个业务入口挂进"业务数据"）。 挂载点由管理员配置，不在子应用的声明里。

10按钮与页面内元素

三段码让按钮级权限自然回归。但实现方式要和常见中后台框架反着来。

关键决策：按钮不落库

常见做法（如 RuoYi）是把按钮作为菜单表里 type=按钮 的行。不要这样： 按钮数量是菜单的 10 倍以上；按钮不需要挂载点/图标/排序/显隐，菜单表的字段对它全是空的； 两个语义混在一张表里，菜单表会退化成权限表。

对象存哪说明
权限码（含 action 级）op_sys_permission按钮的码在这里，来自 definePermissions 声明
菜单节点op_sys_menu只有菜单
按钮本身不落库代码里直接判定，是码的消费者而非被管理对象

管理员在角色页勾选 partner:campaign:publish，按钮就出现了 —— 不需要有人去"配置这个按钮"。

<Can do={P.campaign.publish}><Button>发布</Button></Can>

// 或
const can = useCan();
<Button disabled={!can(P.campaign.publish)}>发布</Button>
必须写进文档第一行

<Can> 是体验，不是安全边界。 真正的门是接口上的 @RequirePermission。 前端藏起来的按钮，直接打接口一样会 403。

11@optimus/permission 包

@optimus/permission
├── (主入口)  零依赖纯核心
│   ├── parse / format / validate      码的解析与校验
│   ├── matches(granted, required)     通配匹配，纯函数
│   ├── evaluate(subject, required)    判定入口
│   └── definePermissions()            子服务声明自己权限的 DSL
├── /react    PermissionProvider / useCan / <Can>
└── /nest     PermissionModule / @RequirePermission
主入口零依赖是硬要求

同一份 matches() 要在四个地方跑：optimus-api 守卫、 partner-service 守卫、optimus-ui 菜单过滤、子应用 iframe 内部。 这行逻辑现在各存一份，正是要消灭的。

与 server-sdk 的差异

@optimus/server-sdk 刻意不做框架集成（"那是消费方三行代码的事，做了反而绑定框架版本"）。 这里可以提供适配，理由不同：那里绑的是通信协议版本，这里绑的只是判定； 且一二方服务全是 NestJS + React。适配放在子路径导出，不用的人零成本。

一处声明，四处消费

// partner-service/src/permissions.ts —— 唯一的声明
export const P = definePermissions('partner', {
  campaign:   ['read', 'write', 'publish'],
  settlement: ['read', 'approve'],
});
消费点写法
后端守卫@RequirePermission(P.campaign.write)
前端按钮<Can do={P.campaign.publish}>
菜单声明{ key:'campaign', path:'/campaign', requires:[P.campaign.read] }
码字典注册发现时一并上报平台
带类型的常量，不是魔法字符串

P.campaign.write 拼错在编译期就报。 这是当前最容易踩的坑 —— 码是自由字符串，错一个字母的表现是"莫名其妙 403"， 排查时很难想到是配置里少了个字母。

12四个视角

A管理员

  • 登记服务一次（baseUrl / embedUrl / 信任级别 / grants），菜单不用管
  • 子应用加了页面 → 出现在「候选入口」，带服务名、声明标题、内部路径
  • 配置一条：标题 / 图标 / 权限码 / 挂载点 / 排序
  • 从不手填 URL 和 path —— 那是发现来的
  • 角色页勾选权限码完成授权
  • 子应用删了页面 → 标红 missing，配置保留，可一键清理

B有权限的用户

  • 侧边栏与静态菜单无任何区别，不知道哪些是子应用
  • 点进去 → 宿主拼 embedUrl + path → iframe 加载对应页面
  • 页面内按钮按 action 码显隐

C无权限的人

  • 侧边栏：自身与全部子节点都不命中 → 整个应用消失
  • 部分权限：顶层降级为分组容器，去掉 path
  • 直敲 URL：宿主页再校验 → 403 页
  • 真正的门：子应用后端 introspect + 权限判定

D子应用开发者

  • 要做：definePermissions 声明 + 暴露菜单 manifest
  • 不需要：登记菜单、填 URL、想权限码、追着运营配
  • 不能：决定谁能看见自己的页面（权限码是平台的体系）
  • 不能：把入口塞进「系统管理」（挂载点由管理员配）
  • 不能：声明别的命名空间的码（注册时拒绝）

子应用接入是各三行

// 前端：握手已经带 perms，直接注入
const ctx = await init({ baseOrigin });            // @optimus/admin-embed（已有）
<PermissionProvider codes={ctx.perms}><App /></PermissionProvider>

// 后端
imports: [PermissionModule.forRoot({ optimusApiUrl })]
// 方法上挂 @RequirePermission(P.campaign.write)
数据链路已经通了

@optimus/admin-embed 的 EmbedContext 已经带 perms: string[] —— 基座握手时就把权限码下发给子应用了。 缺的不是链路，是消费侧的便利。

一条规矩：子应用不画自己的一级导航

平台侧边栏已经是子应用的导航。子应用再画一套，就出现两个事实源， 两边不一致时没人说得清哪个对。

层级谁负责
应用顶层 + 页面级导航平台侧边栏（子应用声明，管理员配码）
页面内部的区块 / 按钮 / tab子应用自己，用同一个 can()

13数据模型

op_sys_permission                    码字典 · 新增
  code            partner:campaign:write
  namespace       partner              ← 注册时校验归属
  resource / action
  title / description
  source          static | service
  service_key     来源服务（source=service 时）
  status          active | missing

op_sys_menu                          菜单树 · 新增
  id / parent_id / title / icon / sort / visible
  source          static | service | document
  service_key
  path            静态路由 或 子应用内部路径
  requires        ["partner:campaign:read"]   ← 权限码数组

op_sys_role_menu                     角色↔码 · 已有，语义不变
  role_id / permission_code
这两张表解决的根子问题

菜单是前端常量，所以"可分配的权限码集合"也只能从前端常量推 —— 这就是 PermissionModal 读 SYSTEM_ROUTES 的原因， 不是写错了，是没有别的地方可读。

两张表落地后，前面聊的合并语义、授不出去、静默丢权限等问题在根上消失。

静态菜单也要入库，理由不是"为了动态"，是让权限集合有权威来源， 同时把排序、挂载点、显隐这些运营该管的东西从代码里拿出来。

14明确不做的

不做理由
ABAC 引擎作为地基
（CASL / Casbin）		 条件规则引用的字段属于 L2 领域模型，平台不该也不能知道；跨进程需序列化 + 三方需装引擎。可以作为 rules 数组里的一条规则接入，但不能是地基 —— 这个区别决定了失效范围
关系图引擎
（OpenFGA / Zanzibar）		 解决资源级 + 层级继承。目前唯一场景是 op_sys_document_perm，为一个模块引入关系图引擎不成比例
集中式 IdP
（Keycloak / Auth0）		 已有自己的认证中心与 introspect，替换伤筋动骨，收益是"标准化"，现在不痛
把 scope 编进码 组合爆炸；scope 语义因业务而异，平台无法统一定义
按钮进菜单表 数量级不匹配，字段大部分为空，两个语义混在一张表
子应用内部 tab 上升为平台菜单 侧边栏臃肿，且管理员要给每个 tab 配码。确有需求时可用码控制，但不出现在侧边栏
现存 CASL 代码的处理

清理与选型是两件事：即便将来子服务内部用 CASL， 平台侧这份空转的也该删 —— 它不是那个用法的起点，是个半成品。 validateAbilityPermissions 看起来像第三道防线、实际每次空转， 这类"看起来在起作用其实没有"的东西最危险（RolesGuard 同类）。

建议单独一次变更清理，不要混进权限重构 —— 混在一起就说不清"接口 403 了到底是删错了还是新模型的问题"。

15迁移与分期

存量 40 个扁平码：一次迁完，不做兼容

已拍板（2026-09-06）

不建兼容层。项目尚未上线，没有存量用户的账号在依赖这批码。 兼容层的代价是双格式解析要维护到"某天有人来清理"——而那天通常不会到来。

直接后果是判定核心只认三段式，实现更简单（少一条解析分支、少一类边界用例）。 代价是重命名必须原子完成：@Perm 声明、 SYSTEM_ROUTES 的 code、op_sys_role_menu 的数据， 三处同时切换。

迁移的可验证性

接口已 fail-closed，迁错会立刻 403，不会静默——错误可见是好事。 但仍需完整对照表 + 回滚脚本，且迁移后要逐个角色实际登录验证菜单与接口。

重命名只改名，不改语义

一个码原先能做什么，迁完还是能做什么（PermUsers → platform:user:manage，而不是趁机拆成 read/write）。 拆分动作粒度是独立决策，等出现真实的"只读角色"需求时按资源逐个拆—— 把重命名和语义变更混在一次做，出问题时分不清是哪一类原因。

16已拍板的决策

下列三点于 2026-09-06 确认，实现按此执行。

① 存量 40 个码：一次迁完，不做兼容
项目尚未上线，没有存量用户在依赖这批码。不要被兼容拖住—— 双格式解析的维护成本会一直挂着，而"某天来清理"通常不会到来。 判定核心因此只认三段式，实现更简单。代价是重命名要原子完成（见第 15 章）。
② @optimus/permission：放在 monorepo
与 @optimus/server-sdk / @optimus/client-sdk 并列， packages/permission。打包方式沿用 server-sdk 那套（零运行时依赖、 tsc 出 dist、node --test 跑编译产物）。 三方需要独立安装时再评估发私有 registry，不预先为此设计。
③ 子应用更深的层级：子应用有自制的权利
平台菜单只到二层（应用顶层 + 声明的页面）。页面内部更深的结构 （tab、区块、分步）由子应用自己用 can() 管，不上升为平台菜单。 若运营确需"某角色只看某 tab"，用 action 码控制即可，不必出现在侧边栏。
这三条对实现的影响

① 让第一期的核心更简单（少一条解析分支）； ② 让第一期可以立刻开工（打包方式已定）； ③ 划清了菜单模型的边界，第四期的 manifest 只需描述页面级，不必支持任意深度嵌套。
