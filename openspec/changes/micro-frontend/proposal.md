# Proposal: micro-frontend — 前端微前端体系(三模式,一份契约)

## 核心诉求

服务端的微服务模式已闭环(服务目录:注册即接入),前端侧要补齐对应的拆分能力:

1. 别的团队/别的技术栈的页面能进管理基座(已有 iframe 通道,需正式化其定位)
2. C 端要能按业务域把整段路径拆到独立应用,各自开发部署互不拖累
3. 未来需要"深度集成"(共享组件树/路由/状态)的模块化拆分时,有一套自己的
   标准可依,而不是临时绑死某个构建器插件

**不引 qiankun/wujie 这类运行时容器框架**:它们解决的是"把任意旧应用塞进任意
基座"的兼容问题,代价是运行时 JS 沙箱(with + proxy)的性能与玄学成本。我们
的子应用都是新建的、可约束的,应当用平台约定(构建时/协议层)换掉运行时魔法
——这与服务端"不引框架,贴 HTTP 契约"是同一个判断。

## 三模式与定位(选型看隔离需求与交互深度)

| | 模式一 iframe | 模式二 Multi-Zones | 模式三 构建时模块(自有标准) |
|---|---|---|---|
| 隔离 | 强(浏览器级) | 中(应用/进程级) | 弱(同运行时,约定隔离) |
| 交互深度 | 低(postMessage) | 中(整段路径,跨 zone 硬导航) | 高(共享组件树/路由) |
| 技术栈 | 任意 | 任意可服务 HTTP 的框架(推荐 Next) | 须遵 Optimus 模块标准 |
| SSR/SEO | 无 | 原生(各 zone 自己 SSR) | 取决于实现 |
| 登录态 | 握手下发 token | 同域 httpOnly cookie 天然共享 | 基座注入 ctx |
| 状态 | **已落地**(服务目录 entryType=embed) | **本方案落地对象** | **只定标准,暂不实现** |
| 典型场景 | 外部团队管理页 | C 端业务域拆分(/activity/* 等) | 深度集成的业务模块 |

## 最终架构一句话

**通道有三种,契约只有一份**:三种模式共用同一个接入面(服务目录 entryType:
embed/zone/module)、同一份上下文契约(token/user/perms/locale/theme)、同一条
权限链(permCode → RBAC → 服务端自校验)。加一种模式是加一个消费视图,
不是加一套体系。详见 design.md。

## 本期交付边界

- 本 change 交付**方案与标准文本**(需求、可行性、架构、Optimus 模块标准 v0 草案)
- Multi-Zones 的落地(第一个 zone 拆出)是后续独立迭代,触发条件:确定第一个
  要拆的业务域
- 模式三明确**不实现**,标准以第一个真实模块需求校准后再实现

## 可行性结论(依据见 design.md 第 6 节)

- 模式一:已被 demo-activity 全流程实证,零风险
- 模式二:Next 官方一等公民(16.x 文档 2026-06 在维),机制只有 rewrites +
  assetPrefix 两件事;C 端认证本来就是同域 httpOnly cookie,登录态共享零改造
  ——**可行性高,成本集中在"拆哪块"的业务决策而非技术**
- 模式三:行业缺位是真实的(nextjs-mf 官方进入弃用流程、peerDeps 止步 Next 15;
  MF 2.0 主战场在 webpack/rspack,Next/Turbopack 无解)——这正是标准要定在
  **产物契约层而非构建器插件层**的原因,可行但必须等真实用例校准
