## Context

order 模块是当前业务模块里体量最大、内部逻辑最复杂的一个：虚拟商品/角色转区/
建公会等多种"产品处理器/校验器"、支付回调（第三方网关）、订单状态机、mock
支付（测试用）。它目前没有与其它业务模块的实际耦合（`order.module.ts` 声明
导入了 `UserModule` 但全库搜索确认 `UserService` 在 order 模块内零调用点，
是历史遗留的多余 import），这一点和 partner-service 迁移前的
"零跨业务依赖"情况类似，属于适合独立拆分的信号。

本次复用 `extract-partner-service` 和 `extract-marketing-service` 已经验证过的
迁移路径，不重新设计方法论。

## Goals / Non-Goals

**Goals:**
- order 模块整体迁移为独立服务，功能行为不变（下单、支付回调、订单查询确认、
  各类产品处理器逻辑）
- 落地前清理 `UserModule` 死依赖
- 验证 SDK 强约束（决策④）在第二个真实迁移场景下依然可行

**Non-Goals:**
- 不在本次实现订单域"待补齐"清单里的能力（SKU 管理后台、退款售后、定价折扣
  联动、财务对账）——这些是后续独立的功能性变更
- 不实现订单域与营销域之间的优惠券/折扣规则联动。这是 design.md
  （中台分层架构文档）明确指出的"典型的不同团队但有真实依赖"案例，一旦要做，
  必须通过 HTTP 接口调用营销域（此时应已作为 `marketing-service` 独立存在），
  不能因为两个域关系近就开始互相读表——但具体怎么联动是另一个变更的范围，
  本次只是先把 order 拆成独立服务，为将来这个联动打好边界基础
- 不处理支付网关本身的账号/密钥迁移（沿用现状的第三方支付配置方式，不是
  本次迁移的范围）

## Decisions

**先做营销域，后做订单域**：`extract-marketing-service` 内部依赖更简单
（只有一处 reward-claim-record → activity 的调用需要清理），订单域内部逻辑
更复杂（多种产品处理器）、且是收入相关的关键路径，出问题的影响面更大。
用营销域先验证一遍"迁移路径 + SDK 强约束"组合在没有 partner-service 那种
`forwardRef` 循环依赖场景下是否顺畅，降低订单域迁移的不确定性。

**删除 `UserModule` 死依赖而不是保留"以防万一"**：全库搜索已确认零调用点，
和 `extract-partner-service` 迁移前删除 `update-mira`/`update-star` 孤儿方法
是同一类判断——确认无遗漏调用方后直接清理，不因为"删除模块导入"这个动作本身
显得风险高就保留一个明确无用的依赖。

## Risks / Trade-offs

**[风险] order 模块的多种产品处理器（角色转区、建公会等）可能存在类似
partner-service 迁移中发现的历史遗留 bug（表名前缀、鉴权挂错类型等），
体量更大意味着排查面更大**
→ 缓解：沿用 `extract-partner-service`/`extract-marketing-service` 建立的
验证方法——迁移过程中发现的零风险历史缺陷可以顺手修复并记录，不视为迁移
引入的新问题，但要预留比营销域更多的验证时间，不按"纯搬运"估工时

**[风险] 支付回调是外部第三方网关发起的请求，迁移后回调地址（域名/路径）
如果发生变化，会导致线上支付回调失败**
→ 缓解：这是本次迁移风险最高的点，需要在 tasks.md 中明确要求：回调路径
本身（不只是内部路由）必须在迁移后保持完全不变，或者提前协调好网关配置
更新的时间窗口，不能等迁移完成后才发现回调断了

## Migration Plan

复用 `extract-partner-service`/`extract-marketing-service` 的迁移路径
（落地前修复 → 骨架搭建 → 业务搬迁 → 服务目录接入验证 → 删除原代码 →
存量单测迁移 → 验收），具体任务分解见 tasks.md，其中支付回调路径的验证是
本次特有的、需要额外关注的一步。

## Open Questions

- 支付网关的回调地址配置是在网关侧后台配置，还是通过某种约定的路径自动
  跟随服务迁移——需要在"落地前修复"阶段确认，如果是网关侧手动配置，需要
  在正式切流前协调好变更时间窗口
  → 已归入 `platform-gateway-topology` 统一处理，不再是本变更独有的
    未决问题。该变更核实到现有生产网关配置（`Caddyfile`）自项目初始化
    后从未跟上任何后续架构变化，本条应在 `platform-gateway-topology`
    完成后重新验证：只要 order 服务的路由前缀和对外可见路径在新拓扑下
    保持不变，回调地址就不受影响；如果新拓扑改变了对外路径结构，才需要
    单独协调支付网关侧的回调地址变更窗口
