## Context

`client-user.controller.ts` 现状只有 `/client-user/profile`、`/client-user/me`
两个自查接口。`ClientUserService` 除了自己模块内和鉴权守卫，没有被任何业务模块
当作"用户资料查询服务"使用。partner-service 的 `PartnerProfileEntity.username`
是"没有跨服务查询能力时，业务方各自存一份会漂移的冗余副本"的真实案例——本次
要补的就是让这类冗余副本不再是唯一选择。

## Goals / Non-Goals

**Goals:**
- 服务能按 uid 查到用户当前的公开资料，不需要自己维护一份会过期的快照
- 查询本身走 service token，明确这是"服务对服务"的调用，不是"用户对用户"

**Non-Goals:**
- 不批量开放用户表的所有字段——只返回明确定义为"公开资料"的字段集合
  （昵称、头像、邮箱、注册时间等），密码、手机号等敏感字段不在返回范围内
  （手机号是否包含需在实现时按现有敏感字段处理惯例确认）
- 不做批量查询接口（一次查多个 uid），本次只做单个 uid 查询，批量场景出现
  真实需求后再评估
- 不追溯修复 partner-service 现有的 `username` 快照漂移问题——那是
  partner-service 自己后续可选的改造，本次只提供查询能力本身

## Decisions

**只接受 service token，不接受 admin/client 用户 token**：这条接口的语义是
"服务查用户"，如果同时接受用户 token，容易演变成"某个用户的 token 被复用去查
别的用户资料"这种权限模糊的用法。收窄到只认 service token，边界更清晰，
也是 `platform-service-token` 这个能力上线后第一个真正的消费场景。

**返回字段是白名单而不是排除敏感字段的黑名单**：显式列出"允许返回哪些字段"，
而不是"排除密码等字段后其余都返回"——后者在用户表未来新增字段时容易在没人
注意的情况下把新字段也暴露出去。白名单方式下，新增字段默认不返回，需要显式
决定要不要加入。

**不做字段级别的按调用方定制返回内容**：所有持有合法 service token 的调用方
拿到的是同一个字段集合，不做"服务 A 能看邮箱、服务 B 看不到"这种按调用方
区分的权限模型——如果未来出现这个需求，属于"服务身份精细化授权"的范畴，和
`platform-service-token` 的 Non-Goals 是同一类问题，留到那时候一起解决。

## Risks / Trade-offs

**[风险] 任何持有 service token 的服务都能查到所有用户的资料，一旦某个服务
被攻破，影响面是全量用户**
→ 缓解：这和现状（每个服务自己维护冗余副本，攻破一个服务只影响它自己那份
过期数据）相比是新增的风险面，需要在实现前明确：这条接口是否要限定"哪些
服务允许调用"（哪怕本次不做精细化字段权限，至少做一层"仅登记在服务目录且
显式标记需要此能力的服务可调用"的开关）——具体方案留到 Open Questions

**[风险] 白名单字段集合选择不当，可能后续频繁变更**
→ 缓解：先按 partner-service 已经验证过的实际需求（昵称、邮箱、注册时间）
定义最小字段集合，需要新字段时走正常的接口变更流程，不预先猜测

## Open Questions

- 是否需要限定"哪些服务可以调用这条接口"（而不是任何持有 service token 的
  服务都能查全量用户资料）？如果需要，落地方式是服务目录新增一个权限标记字段，
  还是在 `platform-service-token` 的范围内一并解决。本次实现前需要先确定，
  影响接口鉴权逻辑的具体实现
