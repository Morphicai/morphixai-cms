## Context

上一迭代（platform-closed-loop）交付了三样本迭代要直接复用的东西：`@Perm` 权限范式、AiService 的模型接入模式（OpenAI 兼容 + 环境变量密钥 + 限频）、以及"新模块四步进场"的路径。本迭代是无代码方向的第一块地基，做的是**协议与闭环**，不是设计器体验——schema 协议定对了，后面往上叠什么都行；定歪了，拖拽做得再漂亮也是返工。

## Goals / Non-Goals

**Goals:**
- 一份 schema 从定义 → 渲染 → 填报 → 数据落库全链路跑通，全程零代码改动
- schema 协议同时驱动前端渲染与服务端校验（单一事实来源）
- 自然语言生成 schema 草稿可用（AI 是加速器，人工确认才落库）
- 公开填报免登录可用且受"启用"开关控制

**Non-Goals:**
- 拖拽设计器、多页表单、字段间逻辑联动（显隐/跳转）——等真实使用反馈
- 数据统计图表——数据查看先做表格
- schema 迁移工具——版本随数据行冻结（见 D3），暂不需要迁移

## Decisions

**D1：自定义精简 schema 协议，不引 JSON Schema / Formily**
JSON Schema 表达力过剩且校验语义复杂（前后端各需引解析库）；Formily 这类方案锁死前端技术栈且学习成本高。自研协议只有 7 种字段类型 + required/占位/选项等有限属性，前端一个渲染器组件、后端一个校验函数就能吃透,两边合计几百行。表达力不够时再扩字段类型,协议演进成本低。

**D2：管理接口挂 `@Perm('FormManagement')`，填报接口 `@AllowAnonymous` + 服务端 enabled 开关双闸**
公开填报是这个模块的价值所在（不登录才能发问卷）。匿名接口只有两个：按 slug 取"已启用"的定义、向"已启用"的定义提交数据；未启用一律 404,不暴露存在性。提交按 IP 限频（复用 ai.controller 的内存计数模式）防灌水。

**D3：数据行冻结 schema 版本号**
定义可以改（schema_version 递增），已提交的数据行记录提交时的版本号。查数据时按行上的版本解释数据,老数据不会因为定义改了变得不可读。这比"改定义就迁移数据"简单得多,而且诚实——历史提交本来就是按当时的表单填的。

**D4：AI 生成走"草稿"而不是"直接保存"**
生成的 schema 先进编辑器预览,人工看过、改过、点保存才落库。模型输出用服务端同一套 schema 校验函数验一遍,不合法就把错误一并返回给编辑器——AI 产物与人写的 schema 走完全相同的入库门,不开后门。

**D5：建表用手写 SQL 不开 synchronize**
库里 31 张表都是显式建的,synchronize 在这个库上是关的（生产惯例）。两张新表的建表语句进 `db/` 目录,与既有做法一致,回滚就是 DROP。

## Risks / Trade-offs

- [公开填报被灌水] → IP 限频（每 IP 每分钟 10 次）+ 单条数据体积上限 64KB + enabled 开关随时可关
- [schema 协议设计不足,后续大改] → 协议里预留 `x-` 前缀的扩展属性位;7 种类型覆盖问卷/报名/工单的主流场景,联动类需求明确划出边界
- [JSON 编辑器对非技术用户不友好] → 接受。本迭代的用户是自己人;AI 生成 + 实时预览已大幅降低手写成本,拖拽是下一迭代的候选
- [匿名接口暴露在公网时的滥用面] → 当前仅本机开发环境;上线前需加验证码或 token,已记为遗留项写入 tasks

## Migration Plan

1. 建表 SQL（op_sys_form_schema / op_sys_form_entry）+ role 1 补 FormManagement 权限码
2. 后端模块 → 前端管理页 → 公开填报页，每步可独立验证
3. 回滚：DROP 两张表 + DELETE 权限码 + revert 提交
