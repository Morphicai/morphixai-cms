# Proposal: i18n-foundation — 多语言能力

## 要解决的问题

CMS 里没有一等公民的多语言能力。现状是两个都不对的东西：
- "翻译管理"菜单 iframe 嵌着一个独立进程的翻译工作台（自带存储，与 CMS 数据完全隔离）
- 各业务（官网文案、后续的文档管理）要多语言时无处可放，只能各自硬编码或塞集合

用户拍板方向：多语言要成为平台能力——先支持"多语言的管理"，后续文档管理等都要挂上来。

## 方案：i18n 键值模块 + 公开读接口 + AI 补全

一个轻量模块，三件事：

1. **存储与管理**：`namespace + key → translations(json, {locale: text})`。
   translations 里有什么 locale 就支持什么 locale——不做语言注册表，加语言就是
   在 json 里多一个键，管理端 UI 默认展示 zh-CN / en-US / ja-JP 三列
2. **公开读**：`GET /api/i18n/:namespace?locale=xx` 返回扁平键值 map，
   C 端与子应用消费；client-sdk 加 I18nSDK（带内存缓存）
3. **AI 补全**：管理端一键"AI 补全缺失语言"——有 zh 缺 en/ja 的键批量翻译，
   走现有 aiService（这也是后续 Agent 化"自动翻译"的能力地基：能力先以按钮形态
   存在并验证，Agent 只是换一个触发方式）

### 为什么不用数据集合存翻译

翻译有 namespace/locale 两个维度、行数以千计、要批量导出——集合的行抽屉模型
（200 行、schema 表单编辑）撑不起这个交互。集合是"业务小数据"的家，翻译是
基础设施，各归各位。

### 与翻译工作台（iframe 版）的关系

并存。工作台是外部工具管它自己的项目文案；本模块是 CMS 自己的多语言存储。
菜单名区分："多语言管理"（新）vs "翻译管理"（旧 iframe）。工作台哪天下线
是它自己的事，本次不动。

### 文章/文档的多语言（明确不做）

内容变体（一篇文档的中英版本）是另一类问题——涉及文章表结构与编辑流。
本次只铺键值层；文档管理要多语言时，在文章表加 locale 变体关联，届时它的
UI 文案部分直接消费本模块。

## 验收标准

1. 管理端"多语言管理"：建 namespace、增删改 key、按语言列编辑
2. AI 补全：只填 zh-CN 的若干 key，一键补全后 en-US / ja-JP 出现合理译文（草稿态，人工可改）
3. 公开接口按 locale 返回扁平 map；未知 namespace 404；缺失 locale 的键回退默认语言
4. client-sdk I18nSDK 消费验证 + 三端构建通过
