## Context

`SITE_DOMAIN`/`COOKIE_DOMAIN` 现状只在 optimus-api 内部读取（`oss.controller.ts`
生成文件绝对 URL、`client-user.controller.ts` 设置跨子域 cookie），没有对外暴露。
这是一个小范围、低风险的能力补充，记录设计只是为了固化"哪些字段算环境信息"
和"谁是唯一来源"，避免后续每个子服务又各自定义一份"环境信息"的形状。

## Goals / Non-Goals

**Goals:**
- 提供一个查询点，回答"当前是哪个环境、这个环境的根域名/cookie 域是什么"
- 保持 optimus-api 现有配置读取方式不变，只是新增一个对外只读出口

**Non-Goals:**
- 不做环境级别的功能开关/灰度配置（那是另一个话题，不混进"环境基础信息"里）
- 不引入新的配置存储（继续用现有的 `.env` + yaml 配置文件机制，不迁移到数据库或
  配置中心）

## Decisions

**只读、无鉴权（或与现有匿名公开接口同等限频）**：环境名/根域名这类信息不是
敏感数据，其它公开接口（`public-dictionary`、`public-i18n`）已经是匿名 + IP 限频
的模式，这个接口沿用同一套约定，不需要 admin/client/service 三种身份中的任何一种。

**返回字段只包含"已经在被读取、已确认有跨服务复用价值"的项**：即环境名、根域名、
cookie 域三项，不预先加入"以后可能需要"的字段（比如 CDN 域名、OSS bucket 前缀）——
等真的有服务需要时再加，避免设计一个没人验证过的形状。

## Risks / Trade-offs

**[风险] 接口匿名可访问，理论上暴露了内部域名结构**
→ 缓解：这些域名本身在浏览器网络请求里已经是公开可见的信息（前端页面本来就在用
这些域名发请求），接口只是把"已经公开的信息"变得可查询，不引入新的信息泄露面
