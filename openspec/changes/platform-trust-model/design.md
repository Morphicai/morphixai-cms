## Context

本变更源于一次架构压测：用"外包团队交付业务服务"和"低代码/AI 生成页面"两个未来
确定要支撑的场景，去检验现有 L0/L1/L2 分层是否成立。

结论是骨架成立——服务目录"登记即接入"、L0 不直接依赖 L2、L2 只能 HTTP 消费 L1
这三条在两个场景下都没被压垮，且外包场景下"停掉某服务只有它自己坏"这个验收判据
是架构天然给出的。**需要补的是信任模型这一层，它现在是空白的。**

三处实证（不是假想）：

1. `packages/optimus-api/src/system/auth/service-token.service.ts` —— 单一
   `SERVICE_TOKEN_SECRET`，`issue(serviceKey)` 可对任意 serviceKey 签发
2. `packages/partner-service/.env.example` —— `DATABASE_USERNAME=root`、
   `DATABASE_NAME=optimus`，与主服务同库同账号
3. `openspec/specs/service-identity-auth/spec.md` —— 防冒充 Scenario 的前提是
   "未持有正确的共享密钥"，即密钥持有者不在防护范围内

## Goals / Non-Goals

**Goals**

- 让"冒充其它服务"在密码学上不可行，而不是靠"别把密钥给不该给的人"这条约定
- 让"这个服务能访问什么"成为**可配置的数据**，而不是散落在各接口里的硬编码判断
- 为三方（外包）服务提供一套可执行的接入约束，而不是口头要求

**Non-Goals**

- 不引入完整的密钥管理系统（KMS/Vault）或证书体系。派生密钥方案在不新增基础设施
  的前提下解决冒充问题，非对称方案留作三方服务真正上线时的升级路径
- 不做服务间调用的细粒度审计/限流（那是独立能力，不在本变更）
- **不拆库**。数据隔离约束只针对 `third-party`；一方服务在 dev 阶段继续共用实例，
  维持 CLAUDE.md 现有约定

## Decisions

### 决策一：密钥派生，而不是逐服务存密钥

三个候选：

| 方案 | 做法 | 取舍 |
|---|---|---|
| a. 逐服务存密钥 | 服务目录存每个服务的密钥 | 密钥必须可逆存储（要验签），数据库泄露即全部沦陷 |
| **b. 主密钥派生**（选中） | `derive(MASTER_SECRET, serviceKey)`，HKDF-SHA256 | 平台只管一个主密钥；派生密钥无法反推主密钥、无法推出别的服务密钥；仍是 HS256，改动最小 |
| c. 非对称 | 各服务持私钥，平台存公钥 | 最干净，但引入密钥分发与轮换管理 |

选 b。**平台侧不存任何服务密钥**——验签时用同样的派生函数现算。这一点很重要：
数据库里没有任何可用于签发的秘密，泄露服务目录表不会导致身份沦陷。

c 保留为升级路径：当第一个真实三方服务上线、需要"平台自己也无法签发该服务的
token"这种更强保证时再切。届时 `trustLevel=third-party` 可作为切换判据。

**派生密钥如何交付给服务**：一方服务由部署配置注入；三方服务带外一次性分发。
本变更不提供在线签发接口——沿用 `platform-service-token` 已确立的"不提供公开签发
接口"这条，避免出现一个"能换取任意服务身份"的端点。

### 决策二：信任级别只给默认值，grants 才是权威

用户明确要求"可以访问什么是可以配置的"。因此**不把能力上限焊死在级别上**：

- `first-party` — 内部团队、同一部署。默认授予全部通用 grants
- `second-party` — 内部但独立团队/独立部署。默认授予常用 grants
- `third-party` — 外包/外部供应商。**默认空**，每一项能力都要显式授予

级别的作用是：① 给新登记服务一个安全的默认起点；② 承载与级别绑定的硬约束
（如三方必须独立库）。真正的判据始终是 `grants` 字段。

**grants 的形态**：服务目录条目上的 JSON 字符串数组，取值为
`<资源>:<动作>` 形式的 grant code，例如：

```
["user-profile:read-basic", "points:grant", "oss:upload", "shortlink:create"]
```

这是"**服务的权限码**"，刻意与用户权限码（`permCode` + CASL）保持形态一致但体系
独立——两者回答的是不同问题（"这个服务能做什么" vs "这个人能做什么"），混在一起
会导致"服务借用户权限"这类越权，那正是当前"借用户 token 转发"模式的问题。

### 决策三：grant 校验发生在被调用方，不在网关

L1 的受保护接口自己校验 grant（经 `@optimus/server-sdk` 提供的辅助方法），不依赖
网关做前置拦截。理由与 `platform-gateway-topology` 的"访问控制发生在权限层而非
网络层"是同一条：网关只做路由，不承担授权语义——否则绕过网关的调用路径
（如 embed 服务浏览器直连）就出现授权真空。

### 决策四：三方服务的数据隔离是硬约束

`third-party` 服务 SHALL NOT 与平台共用数据库实例。这条不进代码逻辑，进**接入
检查清单**（`platform-client-sdk` 的既有 Requirement「新服务接入检查清单」），
与 SDK 强约束一样落到可执行的检查手段上。

理由：应用层的"禁止跨业务 JOIN"对不可信代码提供方无效——他们拿到连接就能读全库。
唯一可靠的边界是连接本身到不了别人的表。

> 一方服务的 DB 账号收窄（当前是 root）不在本变更范围内，但建议单独排一个小改动：
> 每服务一个只授自己 `op_biz_*` 表权限的账号。改动量极小，能把现有的应用层约定
> 变成数据层强制。这两件事目标不同——三方隔离是**必须**，一方收窄是**加固**。

## Risks / Trade-offs

- **BREAKING：现有共享密钥签发的 token 全部失效。** 缓解：当前只有 partner-service
  一个真实服务，且它尚未在任何业务接口上消费 service token（`platform-service-token`
  完成时有意保留了其本地 guard）。实际迁移面接近于零——这正是本变更必须排在
  两个业务域拆分之前的原因，每多拆一个服务，迁移面就多一份。
- **grants 粒度定得太细会变成负担，太粗则失去意义。** 缓解：首批只定义确实已有
  消费方的 grant（user-profile 读、points 发放、oss 上传、shortlink 创建），
  不预先设计一整套权限体系。新增 grant 的成本很低，预先设计的成本很高。
- **派生密钥泄露仍会导致该服务被冒充**（但仅限该服务）。这是对称方案的固有代价，
  可接受——爆炸半径从"全平台"缩小到"单个服务"，且升级到非对称的路径已留好。
- **信任级别可能被误用为"业务重要性"分级。** 它表达的是**代码提供方的可信程度**，
  与业务重要性无关：一个一方服务可以处理核心支付，一个三方服务可以只做活动页。
  文档中需明确这一点。

## Open Questions

留给实施者确认，不是遗漏：

1. **grants 的校验位置在 SDK 还是各接口自己写？** 决策三定了"在被调用方"，但没定
   是做成 NestJS 装饰器（如 `@RequireGrant('user-profile:read-full')`）还是 SDK 的
   显式调用。倾向装饰器（与现有 `@Perm` 心智一致），实施前确认。
2. **主密钥轮换怎么做？** 派生方案下轮换主密钥会让所有服务密钥同时失效。是否需要
   支持双密钥并存的过渡期，取决于届时在线服务数量。当前只有 1 个，可以不做；
   但要在 design 里留明"这是有意省略的，服务变多后必须补"。
3. **`second-party` 现在有真实实例吗？** 如果短期内只有一方和三方两种，三级划分
   可能是过度设计。实施前确认是否先只做 `first-party` / `third-party` 两级，
   给枚举留出扩展空间即可。
